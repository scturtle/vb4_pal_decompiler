# VB4 PAL 逆向说明

本文集中记录 `VB40032.DLL` runtime 与 `PAL.EXE` p-code 的必要逆向结论。
详细过程日志、未证实的 opcode 对照和重复的审查脚本不再单独保留。

## 流水线

```text
PAL.EXE
  -> ProcDsc 签名扫描（恢复过程边界）
  -> VB40032.DLL word dispatcher（恢复指令与 operand）
  -> 栈机反编译（恢复 VB 风格控制流/表达式）
  -> mapping.json（恢复可读名称）
  -> out/pal_code.txt
```

一键运行：

```bash
uv sync
uv run run_pipeline.py
```

产物：

- `out/pal_disasm.txt`：完整 word-pcode 反汇编
- `out/pal_pseudocode.txt`：匿名变量伪代码
- `out/pal_code.txt`：名称重映射后的最终代码
- `input/output_hashes.json`：三个文本产物的 SHA-256 基准

## VB40032.DLL 关键结论

当前 runtime 是带 NB09 CodeView 信息的 `VB40032.DLL`：

| 项目 | 值 |
|---|---|
| ImageBase | `0xF720000` |
| `ENGINE` 段 | `0xF79C000` |
| word dispatch 表 | `0xF7B740C` |
| CodeView 数据 | 文件偏移 `0x105714`，签名 `NB09` |
| handler labels | 1017 个 |
| 有效 word opcode entry | 1034 个，全部精确映射到 CodeView label |
| 相关导出 | `ProcCallEngine`、`MethCallEngine`、`ThunRTMain`、`DllFunctionCall` |

VB4 使用 16-bit word opcode，而不是 8-bit opcode。`ProcCallEngine` 的核心逻辑是：

```asm
movzx esi, word ptr [ebx+4]   ; ProcSize
neg   esi
add   esi, ebx                ; esi = ProcDsc - ProcSize
movzx eax, word ptr [esi]     ; 读取 16-bit opcode
add   esi, 2
jmp   dword ptr [eax*2 + 0xF7B740C]
```

因此原始字节 `FF XX` 是小端 word `0xXXFF` 的一部分，通常是前一条指令的
operand，不是独立的 `FF` 扩展 opcode。CodeView label 由 `src/word_probe.py` 解析，
word 边界和变长指令由 `src/word_probe.py` 根据 handler 的 threaded-dispatch
尾部恢复。

## PAL.EXE 过程布局

PAL 没有 VB6 风格的连续过程表。每个过程布局为：

```text
[p-code bytes][ProcDscInfo]
pc = ProcDsc 地址 - ProcSize
```

`ProcDscInfo` 的关键字段：

- `+0x04`：`ProcSize`（word）
- `+0x08..+0x0F`：恒零，用作签名锚点
- `+0x12`、`+0x18`：恒零

`src/proc_dsc.py` 扫描签名得到 198 个过程，范围约为
`0x403190..0x4276DE`；其中 194 个有 native entry thunk，4 个通过
`MethCallEngine` 间接进入。`ExitProc` 只是单条返回指令，一个过程内可以出现多次，
不能用来切分过程。

分支位移基址是**当前过程的 `codeStart`**，不是全局最大过程起点；
`src/word_disasm.py` 和 `src/pseudo_code.py` 都按当前过程计算目标。

## 重要 operand 格式

普通 word 指令长度由 handler 的 ESI 增量决定。以下变长/特殊格式在
`src/word_probe.py` 中显式建模：

| handler | 编码/长度 |
|---|---|
| `Branch*` | `[disp:i16]`，4 bytes |
| `Gosub` | `[disp:i16]`，4 bytes |
| `AryLdPr/Rf` | `[descriptor:u16]`，4 bytes |
| `GetRecOwner3` | `[payload_offset:i16]`，跳过 payload 后继续分派 |
| `FFreeVar/Str` | `[count:u16][count 个 frame offset]` |
| `NewIfNullAd/Pr/Rf` | `[descriptor:u32]`，6 bytes |
| `LitVarStr` | `[byteLen:u16][offset:i16][UTF-16 text]` |
| `LitStr` | `[index:u16][byteLen:u32][UTF-16 text][u16 terminator]` |
| `ExitProc*/End` | terminator，2 bytes，直接返回 native caller |

字符串字面量直接内嵌在 p-code 流中，不使用 VB6 常量池。

## 调用解析

`src/declares.py` 合并三类信息：

1. PAL Declare 表与 lazy thunk：恢复为 `Pal.xxx`；lazy thunk 的 `slot / 4` 是 Declare 表索引；
2. PE 按序号导入与 `VB40032.DLL` 导出表：恢复为 `VB40032.xxx`；
3. PAL native entry thunk：恢复为 `pub_NNN`/`priv_NNN` 结构名。

VB4 虚调用通过对象接口/vtable slot 间接分派，静态 p-code 中没有唯一的 ProcDsc
地址，因此保留为 `Me.method_NNN` 占位名。事件过程同理，无法仅凭当前证据恢复原始事件名。

## 栈机反编译

`src/stack_ir.py` 使用线性栈机：加载指令入栈，运算指令弹出操作数并构造表达式，
调用指令按照已知签名收集参数，存储指令发射赋值语句。`src/pseudo_code.py` 再做：

- If/Else、For、While、Do/Loop 的结构化恢复；
- 后向 GoTo 的循环转换；
- 前向 GoTo 的 If/Else、simple-skip、Exit For 转换；
- 多目标 If 链的 Select Case 转换；
- ExitProc 目标转换为 `Exit Sub`；
- 行标签和死代码清理。

调用参数数量来自内部过程的栈偏移推导、VB40032 runtime 签名表和 Win32 stdcall
签名表。VB runtime 的 ByRef 临时变量会折叠为 `CStr`、`LTrim`、`Mid`、`Left` 等
VB 风格表达式。

## 变量大小结论

`mapping.json` 使用 DOS 版源码名重映射匿名变量。静态可确认的是槽位大小，而不是
动态数组的实际分配大小：

- `I1/UI1` = 1 byte，`I2` = 2 bytes，`I4/R4` = 4 bytes，`R8` = 8 bytes；
- `Str`、`Rf`、`Pr`、`Ad` 在 Form/global 槽位中都是 4-byte 描述符或引用；
- 数组元素类型/维数可由 `Ary*` 操作码确认；
- `map_data_buf` 等由资源文件加载的动态数组，实际总大小需要资源解析或运行期追踪；
- `NewIfNullPr` 的 `0x0040322C..5C` 是 COM 对象模板，不是数组数据。
