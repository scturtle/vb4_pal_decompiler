# VB4 PAL 逆向说明

本文集中记录 `VB40032.DLL` runtime 与 `PAL.EXE` p-code 的必要逆向结论。
运行方式与产物说明见 `README.md`。

## VB40032.DLL 关键结论

当前 runtime 是带 NB09 CodeView 信息的 `VB40032.DLL`：

| 项目 | 值 |
|---|---|
| ImageBase | `0xF720000` |
| `ENGINE` 段 | `0xF79C000` |
| word dispatch 表 | `0xF7B740C` |
| CodeView 数据 | 文件偏移 `0x105714`，签名 `NB09` |
| handler labels | 1017 个 |
| 有效 word opcode entry | 1034 个，全部精确映射到 CodeView label |
| 相关导出 | `ProcCallEngine`、`MethCallEngine`、`ThunRTMain`、`DllFunctionCall` |

VB4 使用 16-bit word opcode，而不是 8-bit opcode。`ProcCallEngine` 的核心逻辑是：

```asm
movzx esi, word ptr [ebx+4]   ; ProcSize
neg   esi
add   esi, ebx                ; esi = ProcDsc - ProcSize
movzx eax, word ptr [esi]     ; 读取 16-bit opcode
add   esi, 2
jmp   dword ptr [eax*2 + 0xF7B740C]
```

因此原始字节 `FF XX` 是小端 word `0xXXFF` 的一部分，通常是前一条指令的
operand，不是独立的 `FF` 扩展 opcode。CodeView label 由 `src/word_probe.py`
解析；word 边界与变长指令由其 handler 的 threaded-dispatch 尾部恢复。

## PAL.EXE 过程布局

PAL 没有 VB6 风格的连续过程表。每个过程布局为
`[p-code bytes][ProcDscInfo]`，`pc = ProcDsc 地址 - ProcSize`。
`ProcDscInfo` 关键字段：`+0x04` 为 `ProcSize`（word）；`+0x08..+0x0F`
恒零，用作签名锚点；`+0x12`、`+0x18` 恒零。

`src/proc_dsc.py` 扫描签名得到 198 个过程，范围约 `0x403190..0x4276DE`；
194 个有 native entry thunk，4 个通过 `MethCallEngine` 间接进入。
`ExitProc` 只是单条返回指令，一个过程内可出现多次，不能用来切分过程。

分支位移基址是**当前过程的 `codeStart`**，不是全局最大过程起点；
`src/word_disasm.py` 和 `src/pseudo_code.py` 都按当前过程计算目标。

## 重要 operand 格式

变长/特殊格式在 `src/word_probe.py` 中显式建模：

| handler | 编码/长度 |
|---|---|
| `Branch*`、`Gosub` | `[disp:i16]`，4 bytes |
| `AryLdPr/Rf` | `[descriptor:u16]`，4 bytes |
| `GetRecOwner3` | `[payload_offset:i16]`，跳过 payload 后继续分派 |
| `FFreeVar/Str` | `[count:u16][count 个 frame offset]` |
| `NewIfNullAd/Pr/Rf` | `[descriptor:u32]`，6 bytes |
| `LitVarStr` | `[byteLen:u16][offset:i16][UTF-16 text]` |
| `LitStr` | `[index:u16][byteLen:u32][UTF-16 text][u16 terminator]` |
| `ExitProc*/End` | terminator，2 bytes，直接返回 native caller |

字符串字面量直接内嵌在 p-code 流中，不使用 VB6 常量池。

**CodeView 标签别名（#13）**：opcode 0x584/0x586/0x58E/0x590 共享 handler
`FMemLdStr`（0x0F79F138，ImpAd 孪生 0x0F79E344 同理），但指令是**通用
4 字节模块字段载入**（`mov edx,[ebp+8]` 取 Me → `push [Me+off]`，快路径
无任何 BSTR 逻辑）；VB4 无 FMemLdI4，模块级 Long/指针/对象引用全走它。
微软的 NB09 标签以偏概全命名为 Str，而 PAL 的 126 处**零字符串消费者**
（LitI4/CR8I4/GtI4 数值、Declare 句柄、窗体属性操作），故反汇编渲染为
中性名 `FMemLd4`/`ImpAdLd4`（`word_disasm.LABEL_ALIASES`）。安全性：
别名保持 FMem/ImpAdLd 前缀（operand 格式匹配不变），且标量证据表的
数值后缀匹配不到 `…4`（不计证据的语义不变）。

## 调用解析

`src/declares.py` 合并三类信息：

1. PAL Declare 表与 lazy thunk：恢复为 `Pal.xxx`；lazy thunk 的 `slot / 4`
   是 Declare 表索引；
2. PE 按序号导入与 `VB40032.DLL` 导出表：恢复为 `VB40032.xxx`；
3. PAL native entry thunk：恢复为 `pub_NNN`/`priv_NNN` 结构名。

**Declare 语句块（#15）**：表内 77 条（12 字节/条，去重后 74 名，copymen
×3、DrawString×2 同名多签名）渲染为模块级 `Declare Function/Sub
<lib>.<name> Lib "<lib>" Alias "<name>" (…)` 块（remap 后 PAL_ 前缀
名与调用点一致，Alias 保留二进制原名）。三类证据均为静态考古结论：
`sig_off` 是**运行时** API 指针表（`[0x428004]+sig_off`）的槽位偏移，
二进制中**不存在静态参数类型 blob**；返回宽度编译进调用点的
ImpAdCall* 变体（ImpAdCallAd → Function As Long，仅 void 变体 → Sub，
为下界：语句式调用的 Function 也编译为 void 变体）；参数类型由全语料
压栈标签投票（一致则定型，混合则 `As Any`）。二进制里的“错误” Lib 字符
串如实暴露：ShowCursor→winmm、mciSendStringA→kernel32。

**VCall 接收者链（#14，handler 实证）**：接收者链
（ImpAdLdPr/MemLdRf/NewIfNull*/FStAdNoPop/FLdPrThis）走解释器
`[ebp-0x50]` “当前对象”寄存器（FLdPrThis = `mov eax,[ebp+8];
mov [ebp-0x50],eax`，不碰求值栈）；VCallHresult 本身也不压结果
（HRESULT 仅馈错误检查）——是否有返回值是 callee 侧行为，p-code 不可
见，由两遍流水线按活跃性推断（残留到语句边界 = Sub，15/24；被消费 =
Function，9/24）。槽位是接收者自身 vtable 的字节偏移
（`call [[receiver]+slot]`），PAL.EXE 内无 slot→名映射表，故保留
`method_NNNN` 占位名；渲染为 `接收者.method_NNNN(实参)`，接收者不再
泄漏为尾参（旧渲染 24/24 带错）。事件过程同理，无法仅凭当前证据恢复
原始事件名。

**晚期绑定访问（#16，handler 实证）**：`FLdPr`（帧槽对象）与
`FLdPrThis` 同类——把帧槽对象装入 `[ebp-0x50]` 接收者寄存器，零求值
栈效应。`LateIdLdVar mem=stack-N id=XXXXXXXX` 是**零参数**
IDispatch::Invoke 取值：入口硬编码参数个数 0（带参晚期调用是兄弟
opcode，操作数携带 u16 个数，续体 `add esp, 个数×16` 弹参数
VARIANT），worker 发出教科书 `Invoke(obj, dispid=id, IID_NULL,
ctx, wFlags=3(METHOD|PROPERTYGET), {rgvarg=NULL,cArgs=0},
pVarResult=&帧槽, &EXCEPINFO, &puArgErr)`——结果 VARIANT 直写
mem= 帧槽；续体把 &帧槽 压回求值栈，`PopAd`（handler 仅
`add esp,4`）将其丢弃，净零。成员名在运行时由对象 IDispatch 解析，
不可恢复，渲染把槽**别名**为 `recv.lateid_XXXXXXXX`（CStr2Ansi 同型
内联先例）——get 出现在值流入处，未渲染槽位的 Dim 自动消失；
priv_092 两站点复用同一槽，内联避免语句形的先赋值后复用歧义。

**Open 语句（#17，handler 实证）**：`Open flags=XXXX` 的 u16 =
`mode | (access << 8) | (share << 12)`——与 0x0F787D0C worker 的
位掩码一致（mode=低字节，分发臂 1=Input/2=Output/4=Random/8=Append/
0x20=Binary；access=位 8-11，worker 的 `cmp bx,0x300` 证实 3=Read
Write；share=位 12-15）。PAL 唯一一处（0041434E，flags=0104）即
`Open 'WORD.DAT' For Random Access Read As #2 Len = 10`，与
`String * 10` 记录数组、Len=10、顺序 Get 语境互证。未知 mode/access/
share 码不会消失，以 `For ?XX`/`Access ?N`/`' lock=N` 形式可见。

## 栈机反编译

`src/stack_ir.py` 使用线性栈机：加载入栈、运算弹栈构造表达式、调用按
签名收集参数、存储发射赋值。`src/pseudo_code.py` 再做结构化恢复：
If/Else、For、While、Do/Loop；后向 GoTo 的循环转换；前向 GoTo 的
If/Else、simple-skip、Exit For 转换；多目标 If 链的 Select Case 转换；
ExitProc 目标转 `Exit Sub`；行标签与死代码清理。

循环内区域的排放遵循 pcode 地址序（style review #18）：仅分支可达、
地址落在循环 [头, 回边) 区间内的区域，经污点不动点认证（前驱在循环
体外的块污染其后继至不动点；互环前驱为内部边不污染）后，在 Loop
关闭前体内 walk（`_emit_interior_orphans`）——而不是由孤儿趟外提
到 Loop 之后，否则产生 VB4 非法的“跳进 Do 块”边。体内排放位置是
**pre-latch**（#19）：仅主 spine walk（`primary`；臂/leaving 侧 walk
不得触发——其中途 pending 集非孤儿集）访问到 fall 进锁存的块（循环
自然收尾流）且有 due 孤儿时，先把 spine 进入该块的隐式边显式化为
`GoTo L_…`，排完区域再渲染该块——尾部检查保持自然 fall 到 Loop，
无条件跳转后不跟活跃代码（伪死代码读感）；未触发钩子的场景
（pre-latch 块自身 pending，如 inventory E6）回退体末追加，体走查以
隐式 fall→锁存边告终时先显式化为 `Continue Do` 屏障。区域内部 walk
的推迟边若被后续区域块隔断邻接，也必须显式化。同样地，单臂 If 的
臂 walk 停止于非延续点时边必须在臂内显式化（`_arm_stop_edge`）——
If 的 fall-through 拥有 End If 之后的位置，隐式邻接会串边。不可达集
若只含裸跳板、或只渲染出写层必 drop 的尾部出口，则不发
`' ---- unreachable p-code ----` 标记（悬空标记会被误读为“上方代码
已死”，方向恰好相反）。

隐式边的存活由**全域边审计**保障（#19）：walk 的每个隐式转移
（fall 继续与 stop 上传）记录发射位置，过程末对每条边做全路径
到达性模拟（按语句缩进增量重建渲染后的 VB 控制流），要求每条
路径到达目标块首语句且不流入其它块代码；显式跳转语句与 GoTo
穿透裸跳板计为实现。摘要行常开输出 `edge audit: clean`，任何
追加/外提破坏流语义的改动都会在此报出。

调用参数数量来自内部过程的栈偏移推导、VB40032 runtime 签名表和 Win32
stdcall 签名表。VB runtime 的 ByRef 临时变量折叠为 `CStr`、`LTrim`、
`Mid`、`Left` 等 VB 风格表达式；`rtcBstrFromAnsi` 即 `Chr$()`（PAL 的
3 个调用点均为 `Chr(48 + n) & ".RPG"` 存档名构造）。

字符串临时槽的生命周期语义：`FStStrNoPop mem=stack-N` 把栈顶 BSTR 引用
复制到帧槽 N（供结尾 `FFree1Str` 释放）而**不弹出**，帧槽从不被读回
（PAL 全部 29 处验证）。它是纯生命周期管理，不产生源码级赋值；反编译器
不得为它生成语句，否则出现幻影赋值且调用表达式在消费语句里重复一份。

签名推断（style review #2/#7/#9）：内部调用是**全引用 ABI**——参数槽
恒存地址（888 个内部调用点零裸值直压、171 处参数槽直载全是转发），
被调方 I*/F* 只能区分“解引用取值 vs 转发指针”，无法区分 ByRef/
ByVal。修饰符改由**调用点压栈习语投票**决定（两遍流水线：第一遍栈机
给每个实参记来源——裸变量值载+PopTmpLdAd 物化=ByVal 拷贝习语（拷贝
源后缀即类型）、变量本体直压=ByRef 票（恒等优化下弱于拷贝票）、参数
指针转发=弃权并建链；任一拷贝票 ⇒ ByVal，无证据默认 ByRef）；
pointee 类型三层：被调本体解引用证据（ILdI2/IStI2/ILdR8 +
CStr2Ansi/CVarRef 回看）→ 拷贝源后缀 → 转发链 fixpoint 双向传播；
F* 直载的宽度（I4=4 字节地址）不作类型证据。实测 ByVal 参数仅 5 个
（pub_060/pub_099/pub_132/pub_184），269/274 参数有 As 子句。局部与
模块级标量 `Dim` 仍按使用侧 opcode 后缀投票推型（槽内存值，F* 证据
有效，存储证据优先、ImpAd 证据输平局）。

## 模块声明流（declaration stream）

`src/decl_stream.py` 解析窗体模块级变量的声明，数组真实边界不再依赖
运行期：

- 位置：`.text` 内 0x00401A7C（0xBC0，74 条记录），由 `find_stream()`
  扫描 + 结构验证定位；
- 记录 `[tag{u16 字段偏移, u16 kind}]`：`kind=0x0005` 固定数组（12 字节头
  + 归零 SAFEARRAY 模板）、`0x0105` 动态数组、`0x0004` 对象引用；
- 描述符布局由 VB40032 的 `ExDerefAry1/ExDerefAry` handler 反汇编证实；
  元素地址 = idx1 + idx2*bounds[1].cE（列主序），先弹出的下标对
  bounds[0]，即 bounds[0] 对应源码**最后一个**下标，渲染 Dim 时逆序还原；
- 元素类型由使用侧 opcode 推断（`scan_element_usage`）：`Ary1Ld/St` 标量
  后缀；`Ary*Pr/Rf` 后紧跟 `MemLd/St` 且字段偏移 >0 → UDT；紧跟
  `LdFixedStr` → 定长字符串（如 `word_dat_data` 为 `String * 10`）；
- UDT 字段类型同理（`src/struct_types.py`），声明块展开为槽位级匿名类型
  `UDT_fXXXX` 的 `Type ... End Type`：无证据字段默认 Integer，字段表与
  `cbElements` 之间的空洞补 `fXXXX` 占位；重映射只做名称替换，同一
  结构体的多个变量只保留首个 Type 块。

**标量无记录**，存在记录足迹之间的缝隙里。足迹由相邻记录 offset 之差
互证：固定数组 1D=0x18 / 2D=0x20 / 3D=0x28；**动态数组仅 4 字节**
（f01F8 → f020C 的 0x14 间隙里含标量 f01FC 与 6 个 Integer）；对象引用
8 字节；`0x878` 起为窗体控件 COM 槽位区（不在声明流内）。未被足迹覆盖
的引用槽位由 `scan_scalar_usage` 补出标量 `Dim`，实测 143 个，
mapping.json globals 全部有语义名。

槽位大小静态可确认的后缀：`I1/UI1`=1B、`I2`=2B、`I4/R4`=4B、`R8`=8B；
`Str/Rf/Pr/Ad` 在槽位中都是 4 字节描述符或引用。动态数组的实际分配
大小需资源解析或运行期追踪（PAL 唯一的动态数组是 `rng_anim_data`）；
`NewIfNullPr` 的 `0x0040322C..5C` 是 COM 对象模板，不是数组数据。

关键修正（原版声明 vs pal.c 当时猜测）：`battle_sprite_data`/
`battle_sprite_data_ext` 为 Integer(0 To 15) 非 5 元素；
`player_battle_sprite` 10 元素、`battle_role_action`/
`battle_role_data_copy` 8 元素、`battle_action_queue_ext` 10 元素、
`file_offset_table` 为 `Single(0 To 31)`。

三个产物均有体现：`pal_disasm.txt` 头部技术表格 + FMem 行内注释；
伪代码顶部 VB 风格声明块（UDT 的 `As` 类型先为 `UDT_fXXXX`，重映射后为
帕斯卡结构体名）。

## ImpAd 与 FMem 的同基址等价

Form 模块槽位有两条寻址路径，指向同一块模块数据区（`Me` 指针在
stack+8，ImpAd 的 inline dword 相对 p-code global base——同一基址）：

| 入口方式 | 过程数 | 槽位访问形态 |
|---|---|---|
| native entry thunk | 194 | `FMemLd/StI2 mem=stack+8.fXXXX`（含 `Sub_Main`） |
| `MethCallEngine` | 4 | `ImpAdLd/StI2 global=0000XXXX`（事件过程） |

4 个事件过程：`priv_003`（timer_entry_stub）、`priv_092`
（fade_in_or_out_internal）、`priv_163`（timer_midi_cd_callback）、
`priv_190`（init_key_definitions，即 Form_Load）。交叉证据：`priv_190`
写 `ImpAdStI2 global=00000334`，消费方读 `FMemLdI2 mem=stack+8.f0334`；
`Sub_Main` 写 `Me.f0870`，`priv_003` 读 `global=00000870`。

`stack_ir.parse_mem` 已把 ImpAd 的 `global=XXXX` 规范化为 `Me.fXXXX`，
伪代码层不再区分两种形态；`mapping.json` 的 `globals` 是槽位命名的唯一
来源。全程序仅有 5 条 ImpAd 存储：Form_Load 末尾初始化屏幕几何
（`viewport_row_count/stride/limit`、`screen_buffer_ptr=0`、
`max_subfile_size=0`，pal_disasm 00418958-7C）。

## Form 设计期数据（GUI 模板）

`form_count=1`，GUI 表 `@0x401980` 指向 Form 对象 `@0x40263C`（名
`pal`、Caption `仙剑奇侠传 WIN-95 版`，client rect 为 twips）；GUI 记录区
`@0x403118` 为属性包，仅含 `Form1` 的设计器残留与 `PalTimer`
（Interval=1000）；`@0x403180` 起为 VCallHresult 使用的 OLE 接口 GUID。

**结论：Form 设计期数据不含任何 Me.fXXXX 槽位初始值**。槽位全部由
P-Code（Form_Load 或业务代码）或零初始化负责；此前怀疑的“设计期常量”
实为 Form_Load 的 ImpAdSt 写入。PAL.DLL 用 DirectDraw（`g_surf_primary`
等）直接渲染，窗体 client 尺寸与游戏显示无关。
